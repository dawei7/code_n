## General

Process amounts from $1$ through $n$ and maintain `ways`, the ordinary unbounded coin-change table generated by the denominations recovered so far. Before amount $a$ is examined, every recovered denomination is smaller than $a$, so `ways[a]` is exactly the number of combinations for $a$ that do not use a coin worth $a$.

No future denomination can affect amount $a$, because every future value is greater than $a$. There are therefore only two possible target counts:

- If `numWays[a - 1] == ways[a]`, denomination $a$ is absent.
- If `numWays[a - 1] == ways[a] + 1`, denomination $a$ is present. The one additional combination is the singleton coin `[a]`.

Any other difference is impossible and must return `[]`. This decision is forced at every amount, so the reconstruction is unique whenever it succeeds.

After recovering denomination $a$, apply the standard complete-knapsack update in ascending total order: for every total from $a$ through $n$, add `ways[total - a]` to `ways[total]`. Ascending order deliberately permits the new coin to be used repeatedly. The updated table now represents every combination using all denominations up through $a$, establishing the same condition for the next amount.

## Complexity detail

Let $n$ be the length of `numWays`. The outer scan visits $n$ amounts. Recovering denomination $a$ updates at most $n-a+1$ table entries, and in the densest case every amount is recovered. Thus the total work is bounded by

$$
\sum_{a=1}^{n} (n-a+1) = \frac{n(n+1)}{2},
$$

which gives $O(n^2)$ time. The DP table and recovered answer each contain at most $n+1$ values, so auxiliary space is $O(n)$.

## Alternatives and edge cases

- **Subtracting recovered contributions:** One can copy the target counts and remove each newly found coin's contribution in ascending amount order. This is also $O(n^2)$, but the forward DP formulation makes the comparison invariant explicit and avoids reasoning about residual counts.
- **Recomputing coin change after every decision:** Rebuilding a complete DP table from all recovered coins at each amount is correct but can take $O(n^3)$ time.
- **Backtracking over denomination subsets:** Trying both presence and absence for every amount ignores that each decision is forced and can explore exponentially many sets.
- **Empty denomination set:** An all-zero prefix is valid without coins; returning `[]` can therefore represent either that valid set or an impossible input, as required by the output contract.
- **Coin equal to the current amount:** It contributes exactly one new way to that amount, regardless of smaller denominations.
- **Unbounded supply:** The update must run totals in ascending order; descending order would model using each denomination at most once and produce incorrect counts.
- **Large counts:** Counts can be much larger than $n$, but the comparison rule remains exact; implementations need an integer type capable of holding the generated totals.
